# Уязвимости и версии

Консольный инструмент для работы с двумя фидами данных об уязвимостях и версиях продуктов. По названию продукта определяет версии без уязвимостей, а по названию продукта и версии - список актуальных для нее уязвимостей.

Тестовое задание. Реализация на Python 3.10+ и SQLite, без внешних зависимостей в рантайме.

## Выбор стека: почему SQLite, а не Postgres + Docker

Изначально рассматривался "взрослый" стек: **PostgreSQL в Docker** + слой
репозиториев + миграции. Это выглядело бы так (примерно):

```bash
# docker-compose.yml (гипотетический вариант)
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_DB: vulndb
      POSTGRES_USER: vuln
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-vuln}
    ports: ["5432:5432"]
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./schema/postgres.sql:/docker-entrypoint-initdb.d/01_schema.sql:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U vuln -d vulndb"]
      interval: 3s
      retries: 20

  loader:
    build: .
    depends_on:
      db: { condition: service_healthy }
    environment:
      DATABASE_URL: postgresql://vuln:${POSTGRES_PASSWORD:-vuln}@db:5432/vulndb
    command: ["python", "-m", "src.loader", "--feed-dir", "/data"]
    volumes: ["./feed:/data:ro"]

volumes:
  pgdata: {}
```

### Почему отказались в пользу SQLite:

1. **Проверяющему не нужен Docker.** Проект запускается через `python main.py` без внешних программ. Если у ревьюера нет Docker Desktop или прав на его запуск - Postgres-вариант просто не заведется, а для текущего варианта нужен только Python со стандартными библиотеками.
2. **Один файл БД в комплекте.** `data/vulndb.sqlite` кладется в zip, и `python main.py list-products` работает сразу, без `docker-compose up` и без пересборки данных. Для объема в 834 версии / 135 уязвимостей SQLite дает ту же скорость и удобство.
3. **Ноль внешних зависимостей в рантайме.** `sqlite3` - стандартная библиотека Python.
4. **Сложность задачи - не в БД.** Ключевая логика здесь - **семантическое сравнение версий** и **мультификсы** (одна уязвимость закрыта в нескольких ветках). Это вычислительная задача на стороне Python, а не нагрузка на СУБД. Postgres ради `ORDER BY` по строкам, которые все равно нельзя отсортировать без парсера, - оверинжиниринг.

**Что при этом сохранено "на будущее":** слой доступа к данным вынесен в `src/db.py` (тонкий репозиторий), а бизнес-логика в `src/logic.py` не знает, откуда пришли строки - из SQLite или из Postgres. Если завтра понадобится переехать на Postgres, достаточно добавить `src/db_postgres.py` с теми же функциями (`find_products`, `get_versions`, `get_vulnerabilities`) и прокинуть его в `logic`. Остальной код (CLI, REPL, `versions.py`) не меняется. Такой подход дает гибкость без избыточной инфраструктуры сейчас.

## Быстрый старт

Старт учитывает использование приложения, а не разработку. Поэтому `pytest` (requirements.txt) не скачивается, а тесты не запускаются.

### 1. Положить фиды

В архиве уже есть `feed/versions.json` и `feed/vulnerabilities.json` - ничего дополнительно делать не нужно. Если по какой-то причине их нет - скачать архив по ссылке из задания (пароль `clean`), распаковать и положить оба файла в `feed/`.

```bash
feed/
├── versions.json
└── vulnerabilities.json
```

### 2. Собрать БД

```bash
python -m src.loader
```

Ожидаемый вывод:

```bash
Загрузка завершена.
  versions:        ok= 834  dup=0
  vulnerabilities: ok= 135  dup=0
Итог в БД:
  vendors:         17
  products:        24
  versions:        834
  vulnerabilities: 135
  distinct KLA:    105
  DB: .../data/vulndb.sqlite
```

`dup=0` означает, что ни одна строка не была отброшена UNIQUE-ограничениями.

### 3. Запустить консольное приложение

Без аргументов запускает интерактивный режим (REPL) CLI (более подробное описание ниже в "*Интерактивный режим (REPL)*"):

```bash
python main.py
```

С аргументами запускается one-shot режим CLI (примеры использования, более подробное описание ниже в "*Команды CLI*"):

```bash
python main.py safe-versions "VLC media player"
...
python main.py vulns "PostgreSQL" "15.3.1"
...
python main.py list-products
...
python main.py --help
...
```

## Команды CLI

Все команды доступны и через `python main.py <команда>`. Эта версия является one-shot режимом CLI.

### `list-products` - список продуктов в БД

```bash
python main.py list-products
python main.py list-products --json
```

### `safe-versions` - версии продукта без уязвимостей

```bash
python main.py safe-versions "VLC media player"
python main.py safe-versions "VLC media player" --latest
python main.py safe-versions "VLC media player" --json
python main.py safe-versions "VLC media player" --vendor VideoLAN
```

Флаги:
- `--latest` - только самая последняя безопасная версия
- `--vendor` - уточнить вендора (если у разных вендоров продукт с одинаковым именем)
- `--json` - вывод в формате JSON для обработки автоматическими алгоритмами (которые теоретически можно интегрировать)

### `vulns` - уязвимости для конкретной версии продукта

```bash
python main.py vulns "PostgreSQL" "15.3.1"
python main.py vulns "Git for Windows" "2.39.2" --json
```

Один `KLA_id` выводится **одной записью** со всеми `fixed_version` - чтобы было видно, в каких ветках уязвимость закрыта (мультификсы).

### Exit codes

| Код | Когда |
|---|---|
| `0` | Успех |
| `1` | Runtime: продукт не найден, нет БД |
| `2` | Bad input: невалидная версия, неоднозначный продукт |

## Интерактивный режим (REPL)

Запускается при старте главного файла без аргументов:

```bash
python main.py
```

Появляется приглашение:

```bash
Запуск в интерактивном режиме. 'help' — справка, 'exit' — выход.

```

Терминальные команды такие же, как в one-shot режиме CLI (но приложение продолжает работать после исполнения команды, что удобно при необходимости ввода нескольких команд, так как не нужно писать `python main.py` перед каждой из них):

```bash
vulncli> list-products
...
vulncli> safe-versions "VLC media player" --latest
...
vulncli> vulns "PostgreSQL" "15.3.1"
...
vulncli> help
...
vulncli> exit
```

Особенности:
- `exit`, `quit`, `q` - выход из интерактивного режима (остановка приложения)

## Схема БД

DDL - в `schema.sql`. Применяется при каждом запуске `src/loader.py`: файл `data/vulndb.sqlite` пересоздается с нуля.

### Таблицы

```sql
            ┌─────────────────────────────────┐
            │             vendors             │
            ├─────────────────────────────────┤
            │ id     INTEGER PK               │
            │ name   TEXT NOT NULL UNIQUE     │
            └────────────────┬────────────────┘
                             │ 1
                             │
                             │ N
            ┌────────────────▼────────────────┐
            │             products            │
            ├─────────────────────────────────┤
            │ id         INTEGER PK           │
            │ vendor_id  INTEGER NOT NULL FK  │ ──→ vendors(id)
            │ name       TEXT NOT NULL        │
            │ UNIQUE (vendor_id, name)        │
            └────────────────┬────────────────┘
                             │ 1
                 ┌───────────┴─────────────────────────┐
                 │ N                                   │ N
┌────────────────▼───────────────┐ ┌───────────────────▼────────────────────┐
│            versions            │ │             vulnerabilities            │
├────────────────────────────────┤ ├────────────────────────────────────────┤
│ id         INTEGER PK          │ │ id                 INTEGER PK          │
│ product_id INTEGER NOT NULL FK │ │ product_id         INTEGER NOT NULL FK │
│ version    TEXT NOT NULL       │ │ kla_id             TEXT NOT NULL       │
│ UNIQUE (product_id, version)   │ │ description        TEXT                │
└────────────────────────────────┘ │ publish_date       TEXT                │
                                   │ start_vuln_version TEXT NOT NULL       │
                                   │ fixed_version      TEXT NOT NULL       │
                                   │ UNIQUE (product_id, kla_id,            │
                                   │   start_vuln_version, fixed_version)   │
                                   └────────────────────────────────────────┘
```

### Связи

| Родитель | Дочерняя | Кардинальность | Правило |
|---|---|---|---|
| `vendors` | `products` | 1 : N | У вендора много продуктов, продукт принадлежит одному вендору |
| `products` | `versions` | 1 : N | У продукта много версий; версия принадлежит одному продукту |
| `products` | `vulnerabilities` | 1 : N | У продукта много уязвимостей; уязвимость относится к одному продукту |

`versions` и `vulnerabilities` **не связаны напрямую** - связь между ними
вычисляется в `src/logic.py` через диапазон `[start_vuln_version, fixed_version)`.

### Ключевые решения

- **`UNIQUE (product_id, kla_id, start_vuln_version, fixed_version)`** - защита от полных дублей **и** сохранение «мультификсов». Один `KLA_id` может встречаться несколько раз с разными `fixed_version`, если уязвимость закрыта в нескольких ветках продукта. Примеры: `KLA67449` у Git for Windows - 7 фиксов, `KLA77143` у PostgreSQL - 5 фиксов.
- **Продукты с похожими именами - это разные продукты**, не алиасы:
  - `VLC media player` vs `VLC media player (MSI installer)`
  - `Foxit Reader` vs `Foxit Reader Enterprise`
  - `7-Zip` vs `7-Zip (MSI installer)`
  - `Google Chrome` vs `Google Chrome Enterprise`
- **Версии хранятся как текст.** SQLite не умеет семантически сортировать `1.10 > 1.9`, поэтому сравнение полностью на стороне Python. Объем данных - сотни строк, производительность не проблема.
- **`fixed_version` - NOT NULL.** В текущих фидах он всегда заполнен.

### Индексы

- `idx_versions_product` - выборка версий по продукту
- `idx_vulns_product` - выборка уязвимостей по продукту
- `idx_vulns_kla` - группировка по `KLA_id`

## Форматы данных

Формат данных фидов, выданных в начале ТЗ.

### `feed/versions.json`

Плоский массив записей о существующих версиях продукта.

```bash
[
  {
    "vendor": "VideoLAN",
    "product": "VLC media player",
    "version": "3.0.19"
  }
]
```

- `vendor`, `product`, `version` - строки, обязательны.
- Уникальная комбинация - `(vendor, product, version)`.

### `feed/vulnerabilities.json`

Плоский массив записей об уязвимостях.

```bash
[
  {
    "vendor": "Postgresql",
    "product": "PostgreSQL",
    "KLA_id": "KLA52239",
    "description": "RCE vulnerability in PostgreSQL",
    "publish_date": "2023-08-10",
    "start_vuln_version": "15",
    "fixed_version": "15.4.1"
  }
]
```

- `KLA_id` - идентификатор уязвимости (`KLA…`)
- `publish_date` - ISO `YYYY-MM-DD`
- `start_vuln_version` - нижняя граница **включительно**. Может быть неполной: `"15"` означает "все 15.x.x". `"0"` - "с самого начала"
- `fixed_version` - верхняя граница **исключительно**

**Семантика диапазона:** версия `V` уязвима по записи `(start, fix)`, если `start ≤ V < fix`.

## Сравнение версий

Модуль `src/versions.py`. Чисто числовое сравнение, без эвристик.

### Идея

Версия разбирается в кортеж целых компонентов, кортежи дополняются нулями до одинаковой длины и сравниваются поэлементно:

- `1.0 == 1.0.0`, `15 == 15.0.0` - паддинг нулями
- `3.0.11 > 3.0.9` - числовое, не лексикографическое сравнение (`11 > 9`)
- `2.9 < 2.10` (`9 < 10`), `24.09 < 24.10` (`9 < 10`)
- `15.4.0.9 < 15.4.1` (паддинг до `15.4.0.9 < 15.4.1.0`)

### `parse_version(version: str) -> tuple[int, ...]`

Строгий парсер: только ASCII-цифры, разделенные точками. Бросает `ValueError` на:
- Пустых компонентах (`""`, `"1."`, `".1"`, `"1..2"`)
- Знаках (`"-1"`, `"+1"`)
- Подчеркиваниях (`"1_0"`)
- Юникод-цифрах (`"１"`)
- Префиксах (`"v1.2"`)
- Прочем мусоре (`"abc"`, `"1,2"`, `"1.2-rc1"`)

### `cmp_version(a, b) -> int`

Возвращает `-1`, `0`, `1`.

### `is_vulnerable(version, start, fix) -> bool`

Полуоткрытый интервал `[start, fix)`:

| Условие | Уязвима? |
|---|---|
| `version < start` | нет |
| `version == start` | **да** |
| `start < version < fix` | да |
| `version == fix` | **нет** |
| `version > fix` | нет |

Пример (PostgreSQL `KLA52239`, `[15, 15.4.1)`):

```bash
14.9.1  - нет
15      - да (ровно start)
15.3.1  - да
15.4.1  - нет (ровно fix)
17.1.1  - нет
```

Бизнес-логика на реальной БД:

- `vulns_for`: корректные KLA для версии, дедупликация, мультификсы, пустой результат для safe-версии

- One-shot команд
- REPL тестируется без блокировки на stdin
- Корневой `main.py` - через `subprocess.run`, включая запуск REPL с `input="exit\n"`

## Известные ограничения

### UltraISO: слипшиеся версии в фиде

В `feed/versions.json` у UltraISO версии записаны как `9.65`, `9.66`, `9.7`, `9.71`. Судя по прогрессии, вендор имеет в виду `9.6.5`, `9.6.6`, `9.7.0`, `9.7.1` - то есть в фиде потеряна третья компонента (как мы полагаем, либо ошибочно написано `9.7` вместо `9.70`).

Наш парсер трактует версии **чисто числово** (`9.65` = `(9, 65)`), поэтому:

- `9.65 > 9.7` (потому что `65 > 7`);
- `9.65` и `9.66` попадают **выше** `fixed_version = 9.7` и, вероятно, ошибочно считаются "безопасными" по `KLA11360` (диапазон `[9, 9.7)`);
- `safe-versions UltraISO` вернет **все** версии, включая `9.65`, `9.66`;
- `vulns UltraISO 9.65` вернет **пусто**.

**Это баг в данных, а не в коде.** Мы осознанно не применяем эвристики вида "если 2-компонентная версия, то второй компонент может быть слипшимся" - потому что такие эвристики ломают корректную обработку для продуктов с честной числовой нумерацией (`2.9 < 2.10`).

**Решение:** (которое мы не реализовали, сохраняя оригинальные входные данные) привести фид к 3-компонентным версиям (`9.65` в `9.6.5`, `9.7` в `9.7.0` и т.д.). После этого числовое сравнение даст корректный порядок.

### Смешанные компоненты в нотации

Версии в фидах у каждого продукта однородны по числу компонентов. Если в будущем появится продукт со смесью `9.65` и `9.7.0` (2- и 3-компонентные в одном продукте), числовое сравнение даст `9.65 > 9.7.0` (`65 > 7`). Для такого гипотетического случая тоже понадобится исправление фида или явная конфигурация нотации.

### Однопоточный загрузчик

`get_or_create_vendor` / `get_or_create_product` реализованы через `INSERT OR IGNORE` + `SELECT`. В параллельной загрузке второй поток мог бы получить `None`. Для одноразового CLI-загрузчика это не проблема, но явное ограничение.
